## 4A. Audited integration risks and safe proposed implementation slicing (engineering proposal, UNACCEPTED)

This retrospective source audit was performed *after* Q2 production and design #365 governance acceptance. It identifies **why one enormous P4 implementation change should not begin before API/schema/UX dependencies are bounded**:

- **Authored Datum representation:** `src/part/include/simplesolid2/part/part_document.hpp` holds `PartDocumentState::datum_planes` as `std::vector<OffsetDatumPlane>`; `PartDocument::findDatumPlane` and `src/part/part_document.cpp` validate Offset and follow Datum chains under that assumption. Adding only a new `struct EdgePointDatumPlane` without migrating the container, cycle/dependency checking and transaction/API consumers would be structurally incomplete.
- **Native grammar:** `src/part/include/simplesolid2/part/part_document_store.hpp` sets `PartDocumentStore::current_schema_version = 16`. `src/part/part_document_store.cpp` writes `datum_planes` with `kind: offset_plane` and parses only `OffsetDatumPlane` through `parseDatumPlanesV10`; real legacy v16 roundtrip and unknown-kind rejection tests are mandatory **before** enabling a new authored Datum kind.
- **Derived frames:** `src/part/datum_evaluation.cpp` evaluates existing Offset Datum chains and status/Body dependency. `kernel::Frame3::valid()` in `src/kernel/profile_input.cpp` only establishes finite, nondegenerate right-handed input, **not** orthonormal axes or edit continuity. Prefer a separately validated, dedicated frame-construction contract; do **not** weaken global `Frame3::valid()` or change the Kernel API as a shortcut.
- **Application/user actions:** `src/application/datum_plane_draft.cpp` already has create/edit, generation and Finish validation, but its current `reverse()` negates **offset distance**, not new `EdgePointDatumPlane` `V,N` signed orientation. A future new-constructor Reverse must not accidentally invert legacy Offset meaning. `src/ui/cad_workbench.cpp` and existing Datum/Sketch/Command Line tests must retain one tool and current input parity.
- **Unresolved endpoint case:** Q1 requires an independently certified semantic terminal Point. A real globally Ambiguous/Unsupported Point is not made durable merely by a new Datum constructor; the intended shared-corner Edge B UX needs explicit source-provenance evidence or a precisely scoped follow-up, never automatic nearest XYZ/native endpoint or silent global Point promotion.
